1. 結論

前提：インタプリタが go に勝てる根拠は「表層だけ読む」と「必要になるまで読まない（遅延）」の 2 つだけです。この 2 つが効かない処理で負けるのは自明で、以下の結果もその通りに分かれました。

  • 勝てる場所ははっきりしている。対象コードベースの型や宣言を表層だけ読めばよい同期タスクでは、minigo は 0.02 s で答え、モジュールが無くても動きます。同じ情報を型付きで読む道具（代理として go vet）は、clickhouse で cold 17.4 s、grafana の pkg/api では cold 97.4 s・ピーク 2.8 GB かかります。
  • 標準ライブラリだけで済むスクリプトでは負ける。go/parser で grafana の API 定義を走査する grafana-openapi は、minigo 3.29 s に対し go run は cold 1.90 s、warm 0.05 s です。インタプリタの実行速度そのものが問われる場面で、ここは今後も勝ち目がありません。ただしインタプリタ性能のベンチマークとしては有用です。
  • 改善の余地はまだ大きい。CPU の約 37% が GC とスケジューラで、アロケーション 2.11 GB の 34% がフレーム確保です。GC 設定だけで実測 −8%、フレームのプール化などを重ねれば 2 s 前後までは見込めます。
  • 「実態」の穴。3 タスク中 2 つは go/parser で全ファイルを読んでおり、表層読みも遅延も効いていません。理由は、inspect が関数本体（ルート登録）と定数初期化子を見られないことです。ただし swagger:route の注釈は 121 件中 117 件がメソッドの doc コメントで、inspect.Doc で読めるので、タスク側の作りにも改善の余地があります。売りが一番効くはずの「grafana の大きなパッケージを表層で読む」タスクは、まだハーネスにありません。

2. 答えが出るまでの時間（ビルド + 起動 + 実行）

各行で minigo と、同じ答えを出すネイティブの手段を比べます。ネイティブは「キャッシュあり（warm）」と「空の GOCACHE（cold）」の 2 点です。横軸は対数目盛です。

minigo は常に毎回ソースから読むので cold/warm の区別がありません（minigo 本体のビルドは別途 1 回だけ、cold 3.6 s）。grafana 2 タスクのネイティブは go run .、clickhouse-settings のネイティブは同じ情報を型付きで読む go vet ./pkg/plugin を代理にしています。

5. 改善の余地（効きそうな順）

  1. GC 設定を CLI で上げる（例: debug.SetGCPercent(400)）。実測 −0.26 s（−8%）。数行で済み、最も安い。スクリプト用途ではピークメモリが小さいので副作用も小さい。
  2. フレームのプール化（prepFrame、アロケーションの 34% = 0.73 GB）。GC が CPU の 22% を占めるので、ここが一番大きな塊。見込み −0.3〜0.5 s（推定）。TODO 済み。
  3. スタック確保と値の箱詰め（frame.push 12%、runtime.Tag 11%）。スタックの事前確保や、タグ付けで新しい値を作らない工夫。
  4. インターフェース判定でのメソッド集合の 2 重走査（methodWalkU、アロケーションの 16%、CPU 約 5%）。1 回の走査で両方の形を作る。キャッシュするなら REPL 向けの無効化が要る。見込み −0.15 s 程度。TODO 済み。
  5. #485 のセレクタ変更の見直し（変数のフィールドを読むだけの x.f でも参照を作っている。参照が要るのはポインタレシーバのメソッド呼び出しだけ）。以前の計測で約 0.2 s。TODO 済み。

全部入れても 2 s 前後と見込まれ、go run warm の 0.05 s には届きません。性能改善の目的は「標準ライブラリだけのスクリプトで勝つこと」ではなく、「重い処理が混ざっても 3 分の痛みの閾値から十分遠くにいること」と、インタプリタのベンチマークとしての健全さです。

7. 計測方法と注意

  • minigo の時間は realworld/run.sh の 3 回実行（#534: 3.38 / 3.29 / 3.26 s の中央値）。同じ時間帯に main（#531 まで）は 3.45〜3.49 s。
  • ネイティブの cold は、毎回新しい一時 GOCACHE で測定。ユーザーのキャッシュは消していません。モジュールキャッシュは取得済み（grafana は約 5 GB）。
  • 不完全な環境は、空の GOMODCACHE + GOPROXY=off で再現。
  • プロファイルは realworld/prof と同じ方法で、実行トレースなしで 2 回取得（結果はほぼ同じ）。
  • grafana の go vet は go.work のワークスペースモードで実行（-mod=mod は使えないため）。
  • 推移グラフの点は計測した時間帯が異なります（同じマシン）。
